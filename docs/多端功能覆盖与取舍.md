## 三、RN 的特殊性：它不是一个 UI，是两个产品

| 角色 | 需要什么 | 现状 |
|---|---|---|
| 买方（发包） | 提交任务、看进度、下载、账单 | **几乎空白**（只有登录和设备信息） |
| 卖方（贡献算力） | 常驻前台 Service、设备探测、接单、回传、收益 | **相当完整**（Kotlin 侧全链路） |

这两条线放在同一个 App 里没问题（`apps/mobile-rn` 的定位就是「一个 App 两副面孔」），
但**优先级必须排清楚**：如果手机端的主要价值是「让闲置手机贡献算力」，那买方四项的
权重可以低；如果它也承担「随手发个转码任务」，那 L0 必须补齐。

建议：**卖方优先，买方保底**。买方四项做到「能提交一个小样、能看进度、能复制下载链接、
能看余额流水」即可，不做高级参数（编码器/分片数/服务端路径）—— 那是桌面端的事。

## 四、要不要「全端全功能」：过三个筛子

**筛子 1 — 物理上成立吗？**
小程序传不了 2 GB 视频（无分片续传）、不能后台常驻、没有 WebRTC；手机屏幕拖 ComfyUI
节点画布是自虐；RN 也没有「选择项目文件夹」的文件系统权限。

**筛子 2 — 主场在哪？**
服务挂牌要传图、写长描述、来回砍价；模型网关要填 base_url / key / 配额。这类「长表单 +
大文件 + 多轮协商」的主场永远是键盘和大屏。

**筛子 3 — 边际用户有多少？**
卖方要随身看收益，但配置节点必然回电脑前；买方多数在剪片子的电脑前。

结论：**核心功能不该平铺到 5 端，而该按端定级。**

## 五、鸿蒙的分岔：套壳还是原生节点

这是本轮最需要拍板的地方，因为它决定「手机端 = RN」这个等式是否成立。

**事实一：现在的鸿蒙端不是 RN。** `apps/harmony/.../pages/Index.ets` 是一个 ArkWeb
`Web` 组件，加载 `rawfile/web/index.html` —— 改造前那是 `apps/mobile/dist` 的副本
（没有 `build.json` 的旧产物）。所以当时鸿蒙用户看到的是**废弃的 UI**；
2026-11-15 已换成 `web-react/dist`，`apps/mobile` 本身已于 2026-11-20 删除。

**事实二：RN 跑不了鸿蒙。** RN 0.88 + Expo 58 没有鸿蒙目标；要复用 RN 代码得走
RNOH（React Native OpenHarmony），而 Expo 模块（expo-status-bar、AsyncStorage 等）
在 RNOH 上基本要重写 ArkTS 侧 —— 实际工作量不比原生小。

**事实三：套壳当不了节点。** WebView 里的页面切到后台会被系统挂起，常驻长轮询与
MediaCodec 转码都跑不住。安卓那边正是因此才把节点逻辑放进 Kotlin 前台 Service。
想在鸿蒙提供算力，必须走 ArkTS 的 `backgroundTaskManager` 长时任务 + 原生解码。

三个选项：

| 选项 | 做法 | 成本 | 鸿蒙能不能当节点 |
|---|---|---|---|
| **A 只做买方** | 套壳继续，但 `rawfile/web` 换成 `web-react/dist` | **1 天** | 不能 |
| B 原生节点 | ArkTS 重写 NodeService + SegmentCutter + 解码侧 | 1–2 周，且解码能力要重新验证 | 能 |
| C RNOH | 复用 RN 业务层，原生模块重写 ArkTS | ≥ B，Expo 生态还要剥离 | 能 |

**建议选 A，并把 B 设为「鸿蒙用户真的有贡献意愿时」再做。** 理由：鸿蒙 NEXT 的设备量、
你的毕设时间线、以及「节点供大于求时需要的是质量不是数量」这三件事都不支持先做 B。
选 A 之后，鸿蒙就是一个**只读买方端**，与小程序同级，不再需要独立维护 UI。

> **2026-11-15 决策：选 B（ArkTS 原生节点）。**
> 即鸿蒙最终要跑 `backgroundTaskManager` 长时任务 + 原生解码，与 RN 的 Kotlin 实现
> 是**两套节点代码、同一套 Broker 契约**。
> 当前状态：交付形态先按 A 落地（rawfile 已换成 `web-react/dist`，买方端今天就能用），
> B 的 ArkTS 节点作为独立工程排期，见第九节。

如果坚持要鸿蒙也当节点，请明确：安卓 = RN 节点，鸿蒙 = ArkTS 原生节点，
**这是两套节点实现**，共用同一个 Broker 契约（`/api/worker/hello`、claim、report 都一样），
可以共用的只有协议，不是代码。

## 六、分级契约（修订版）

### L0 · 交易主链 —— 所有在用端必须完整

登录/注册 · 余额 · 提交任务 · 任务进度 · 下载产物 · 账单流水

现状：web-react ●、内嵌单页 ●、小程序 ●、RN ●（五项买方功能已补齐）。
RN 仍是「卖方为主、买方保底」：卖方能力最全，买方只做最小闭环。

### L1 · 桌面主场 —— 只在 web / exe / 内嵌单页

服务挂牌与交易会话 · 模型网关 4 Tab · 云主机 · 论坛发帖 · 生图生视频 · 管理面

现状：只有 web-react 完整；exe 现在也没有（它的脸是废弃的 mobile）。**这是 exe 换脸后
自动获得的能力** —— 这也是为什么换脸优先级最高。

### L2 · 手机主场 —— 安卓 RN（+ 鸿蒙待定）

常驻贡献算力 · 一键接入/扫码 · 余额速查 · 收益通知 · 拍照发帖

现状：RN 的常驻节点已经是最完整的一环。

### L3 · 单端独占 —— 明确不移植

| 能力 | 独占端 | 理由 |
|---|---|---|
| ComfyUI 工作台 | web-react | 画布交互 + 116 KB 引擎 |
| 管理面 | web-react/admin | 运维操作，不进手机 |
| Windows worker 子进程 | exe | 依赖 Windows 进程模型 |
| Kotlin 前台 Service | RN 安卓 | 依赖 Android 前台服务 |
| ArkTS 长时任务 | 鸿蒙（若做 B） | 依赖 HarmonyOS 后台任务 |

## 七、路线与执行状态

### 第一步 ✅ 已完成（2026-11-15）：给 exe 换脸

1. `StarStack.Desktop.csproj` 的 `EmbeddedResource` 改为 `..\..\web-react\dist`，
   `EnsureWebBuildStamp` 同步改路径；
2. **反代放在 `MainWindow.xaml.cs` 的 `OnProxyRequest`**（WebView2 `WebResourceRequested` 拦截），

**下载那个坑**（值得单独记）：`/download/{id}` 要 Bearer，`Linking.openURL` 会 401。
正解是 `FileSystem.downloadAsync(url, target, { headers: { Authorization } })` 把 token 塞进请求头，
再交给 `Sharing.shareAsync` 落盘 —— 手机没有「另存为」，只能借系统分享面板。

**手机端买方是「保底」，不是「等价」**：只留最必要的三项参数（画质/CRF/时长），

验收：`npx tsc --noEmit` 通过；`verify-console-sync.cjs` 的 L0 矩阵五端全绿。

| 让鸿蒙也供算力 | 第五节选项 B（已定），见第九节 |
| 只维护一套 UI | web-react 做买方全功能，RN 做手机+节点，其余全是壳 |

## 九、鸿蒙 ArkTS 原生节点：实施要点

决策已定 B。下面是动手前必须先想清楚的四件事，不是清单，是坑。

### 1. 长时任务不是「申请一下就能跑」

`backgroundTaskManager.requestSuspendDelay` 只给**短时延后挂起**（约 3 分钟级），
真正的常驻需要 `startBackgroundRunning` + 对应 `BackgroundMode`（如 `dataTransfer`），
且必须在 `module.json5` 声明权限、通知栏常驻。

**推论**：节点循环的心跳间隔要按系统允许的后台窗口设计，不能照搬 Android 前台 Service 的假设。

### 2. 分片执行要重写，不能复用 ffmpeg 命令行

RN 那边用的是 `MediaExtractor + MediaMuxer`（Android API）。鸿蒙的对应物是
`@ohos.multimedia.media` 的 `AVDemuxer` / `AVMuxer` / `AVCodec`，接口形态不同，
`SegmentCutter` 与 `MediaCodecTranscoder` **要按 ArkTS 重写**，但切分策略（IDR 对齐）
与回传契约可以照抄。

### 3. 契约一致，代码不共享

两套节点必须严格对齐这几件事，否则同一个分片在两端行为不一致：

| 契约点 | 说明 |
|---|---|
| `POST /api/worker/hello` | 注册上报 `os/arch/cpus/mem/runtimes`，鸿蒙端 `os` 建议 `harmony` |
| 认领与租约 | 长轮询节奏、25s 心跳、409 迟到回传不二次结算 |
| 双 SHA-256 | 下载源片校验 + 回传产物校验，节点侧自己算一遍 |
| 能力声明 | `runtimes` 里要不要声明 `transcode`，取决于鸿蒙解码能力验证结果 |

### 4. 派发匹配要先改后端

调度器按 `os/arch/runtimes` 匹配节点。鸿蒙节点上线前，Broker 的匹配逻辑与
`policy.launch_harmony` 这类开关要一起加，否则节点注册上来却永远接不到活。

**建议顺序**：先做「能注册、能认领、能跑一个分片、能回传」的最小闭环（约 1 周），
再补能力探测与并发槽，最后才谈 GPU 与多格式。
