## 0. 一页速览

**要解决的问题**：平台早期没有真实算力提供方入驻，模型网关 `/v1/chat/completions` 没有可路由的上游，买家拿到 key 也调不通。需要平台自己先充当第一个供给方，把几家正规大模型厂商的 OpenAI 兼容端点接进来。

## 1. 背景与判断

共享算力平台天然鸡生蛋：没有模型可调，买家不来；没有买家，节点方不进。行业通行解法是平台先当第一个供给方，等真实供给起来再退出。这件事不是跑偏——它本身就是"调度 + 交易中间层"的最小可运行形态，后续真实 provider 接入后可以原地替换。

对外表述统一用「**官方供给 / 平台自营节点**」，不要用「中转站」。

**经济模型必须先说清楚**（这一点容易搞错）：

- 买家按 `price` 扣点，扣的钱 100% 归平台侧：90% 通过 `recordContribution` 记到上游 owner 账户（[internal/hub/gateway.go:1355](../internal/hub/gateway.go)），10% 是撮合费，留在平台。
- 所以当 owner 就是平台账户时，**平台拿到的是售价全额**，真实成本是厂商账单。定价只需覆盖厂商成本并留利润，**不需要再额外加 10%**。
- 目前公网档 `Recharge: false`（[internal/hub/policy.go:89](../internal/hub/policy.go)），没有支付渠道。也就是说自营上游上线后，消耗的其实是"新用户赠额"对应的真金白银。这是 §4 第 4 个输入项存在的原因。

## 2. 硬约束（违反即返工）

1. **单进程**：不新增服务、不新增监听端口、不引入新的数据库或消息队列。
2. **契约不变**：`/v1/models`、`/v1/chat/completions`、SSE、`X-Starstack-*` 响应头全部保持现状。厂商的额外字段原样透传即可。
3. **自营上游 = 普通上游**：走同一张 `upstreams` 表、同一条路由、同一套结算。不要为它写特殊转发分支。
4. **凭据**：厂商 key 只允许出现在服务端 env 文件或控制台录入中；入库必须经 `secretBox.seal`（AES-GCM）。任何日志、错误响应、测试夹具里都不得出现明文 key。
5. **上游选型白名单**：只接厂商官方端点或明确的聚合平台（OpenRouter 等）。禁止接入转售/拼车/来源不明的 key。
6. **启动韧性**：播种失败（env 缺失、DNS 不通、厂商 4xx）只能打日志，**不能让 broker 启动失败**。
7. **正式产物构建**：二进制构建/打包走 1145 构建节点的平台 build 任务，不要在本机产出上线产物；本机只允许跑 `go test` / `go vet` / `go run` 做开发验证。1145 不可达时先问用户，不要自行改用本机交叉编译上线。

## 5. 任务清单

### P0-1 启动时播种平台自营上游

**改哪里**

- 新建 `internal/hub/gateway_seed.go`（与现有 `gateway.go` 同包，可直接复用 `validateUpstreamURL`、`normalizeModels`、`normalizeCaps`、`secretBox`）。
- 在 [cmd/server/main.go:141](../cmd/server/main.go) `hub.NewServer(...)` 之后调用播种函数。

**env 约定**（全部可选；不配则完全不播种，行为与现在一致）

```bash
# 自营上游列表，JSON 数组，单行
STARSTACK_SEED_UPSTREAMS='[
 {"name":"DeepSeek 官方","base_url":"https://api.deepseek.com",
  "api_key":"sk-xxxx","models":["deepseek-chat","deepseek-reasoner"],
  "cost_in_yuan_per_1k":0.002,"cost_out_yuan_per_1k":0.008,"markup":1.35,
  "max_context":65536,"caps":["tools","json_object","prefix_cache"]},
 {"name":"硅基流动","base_url":"https://api.siliconflow.cn/v1",
  "api_key":"sk-yyyy","models":["Qwen/Qwen3-32B"],
  "cost_in_yuan_per_1k":0.002,"markup":1.35,
  "max_context":32768,"caps":["tools"]}
]'
STARSTACK_PLATFORM_USER=starstack-platform
STARSTACK_PLATFORM_PASSWORD=...
STARSTACK_POINT_YUAN=0.01
```

**行为要求**

1. 解析 JSON 失败 → 打日志并跳过，不阻断启动。
2. 找 `STARSTACK_PLATFORM_USER`；不存在则用 `auth.ValidName` / `auth.ValidPassword` 校验后创建（`auth.NewSalt` + `auth.Hash` + `auth.Iterations`，见 [internal/hub/users.go:137](../internal/hub/users.go)）。缺密码时不要创建账户、不要播种，打一条明确日志说明原因。
3. 每条上游：`validateUpstreamURL(base_url, s.policy.Public)` → `normalizeModels` → `normalizeCaps` → `secretBox.seal(api_key)` → `CreateUpstream`。
4. **幂等**：以 `owner + 小写 base_url` 判断是否已存在，存在则跳过并打日志（"已存在，跳过"）。不要重复插入，也不要在启动时覆盖用户在控制台改过的价格/开关。
5. 价格：给了 `price` 就直接用；否则 `price = round4(cost_in_yuan_per_1k / STARSTACK_POINT_YUAN * markup)`，`price_out` 同理；`markup` 缺省 1.2。
6. 播种完成后对每个上游调用一次 `probeUpstream`（[internal/hub/gateway.go:945](../internal/hub/gateway.go)），把厂商实际返回的模型列表打日志；配置里的模型 ID 不在其中时打 **warn**，但保留配置（厂商模型名大小写/别名差异很常见，不能因此拒启）。
7. 任何一条失败都只影响该条。

**验收**

- 不配 env：启动行为与改动前完全一致，日志无噪音。
- 配置两条：`/api/models/catalog` 出现两家上游计数；重启第二次不产生重复行。
- 数据库里 `upstreams.api_key_enc` 是密文，不等于明文；`grep -r "sk-" 日志文件` 无命中。
- 假 key + 真地址：启动不崩，probe 失败只打日志。

### P1-1 每 key 日限额 + 平台日预算熔断

**为什么**：公网档没有充值，赠额烧完之前必须有人为上限；否则一把泄露的 key 就能把当日预算打光。

**改哪里**

- schema：[internal/store/store.go:152](../internal/store/store.go) 附近加表；[internal/store/store.go:356](../internal/store/store.go) 的 `columnMigrations` 加 `ALTER TABLE api_keys ADD COLUMN daily_quota REAL NOT NULL DEFAULT 0;`（0 = 不限）。
- 新增表：`gateway_spend(key_id TEXT NOT NULL, day TEXT NOT NULL, credits REAL NOT NULL DEFAULT 0, requests INTEGER NOT NULL DEFAULT 0, PRIMARY KEY(key_id, day))`。
- store 层：`AddGatewaySpend(keyID, day, credits)`（UPSERT）、`GatewaySpendToday(keyID)`、`GatewaySpendAllToday()`。
- hub 层：`handleV1Chat` 目前丢弃了 key（`u, _, ok := s.gatewayUser(...)`，[internal/hub/gateway.go:1048](../internal/hub/gateway.go)），改为接收 `key`；在算完 `reserve` 后（[internal/hub/gateway.go:1151](../internal/hub/gateway.go)）、查余额之前做两项检查：
  - key 限额：`spent + reserve > key.DailyQuota` → 429 `insufficient_quota`，文案说明"该密钥今日额度已用完"。
  - 平台预算：`STARSTACK_GATEWAY_DAILY_BUDGET`（点，0=不限）> 0 时，`allSpent + reserve > 预算` → 503 `platform_budget_exhausted`。
- `settleGateway` 增加 `keyID` 参数并在结算处写入实际 `cost`；三个调用点：[internal/hub/gateway.go:1238](../internal/hub/gateway.go)、[1254](../internal/hub/gateway.go)、[1274](../internal/hub/gateway.go)。`gatewayRefund` 路径不写 spend。
- 控制台：建 key 时接受 `daily_quota`，key 列表展示今日已用（[internal/hub/web/index.html:3103](../internal/hub/web/index.html) 附近）。

**注意**

- 预扣是请求前的悲观估算，并发请求可能轻微超出日限额，这是可接受的；不要为此加全局串行锁。
- 不要改动"余额不足"的既有语义（402），日限额用 429 区分。

**验收**

- 单测覆盖：额度为 0 不限；额度 0.1 + 预扣 0.2 → 429；跨天归零。
- 平台预算设为 0.01 后第二次请求被 503；重启后当日累计不丢（落库，不放内存）。

- [ ] 余额不足仍返回 402；日限额触发返回 429（P1-1 完成后）。
- [ ] 公网档校验：`--public` 下把 base_url 指向 `127.0.0.1` 会被拒（`validateUpstreamURL` 的私网拦截）。
- [ ] 重启 broker，上游与当日 spend 均保留。
- [ ] `git status` 中不出现任何 key、`gateway.key`、`data-*` 目录。

## 7. 部署（需用户明确同意后才执行）

1. 构建：走 1145 构建节点的平台 build 任务产出 `linux/amd64` 的 `starstack-server`（不要本机交叉编译上线）。
2. 写入 env：把 `STARSTACK_SEED_UPSTREAMS` / `STARSTACK_PLATFORM_USER` / `STARSTACK_PLATFORM_PASSWORD` / `STARSTACK_POINT_YUAN` / `STARSTACK_GATEWAY_MAX_PROMPT` / `STARSTACK_GATEWAY_DAILY_BUDGET` 追加到服务器 `/etc/starstack/env`；权限保持 `640 root:starstack`；**改完不要把文件内容回显到终端或聊天**。
3. 上传与重启：沿用 [deploy/deploy.sh](../deploy/deploy.sh) 的第 3/4 步（scp 到 `/tmp` → install → `systemctl restart starstack`），或按已有运维流程执行。
4. 冒烟：`journalctl -u starstack -n 100` 看播种日志；`/v1/models` 用一把新 key 能列出模型；发一条真实 completion。
5. 观察 10 分钟：网关日志无 5xx 堆积，`gateway_spend` 有增长，平台账户 `Earn` 在涨。

**服务器约束**：该机内存约 891 MB，systemd 已限 `MemoryMax=512M`（[deploy/starstack.service](../deploy/starstack.service)）。新增的表与索引都很小，不要引入任何常驻缓存/大对象。

## 8. 回滚

- 代码回滚：换回上一版 `starstack-server` 并 `systemctl restart`。
- 只停自营、不换二进制：控制台对自营上游 `PUT {"enabled":false}`，或把 `STARSTACK_SEED_UPSTREAMS` 置空重启（已存在的行不会被删除，只是不再新增）。**不要**用 `DELETE FROM upstreams` 清理，会连带丢掉历史关联。
- 数据库变更全部是"加表/加列 + 默认值"，旧代码可正常读取，无需回滚 schema。

## 10. 已知坑与反模式

1. **模型 ID 必须逐字匹配**。路由用 `EqualFold` 比对，且请求体原样转发（[internal/hub/gateway.go:1294](../internal/hub/gateway.go)）。厂商叫 `Qwen/Qwen3-32B` 就登记这个，不要自己起别名。
2. **能力声明宁少勿多**。多声明一个 `tools` 会把带工具的请求送进不支持的上游，用户看到的是上游 4xx。不确定就不声明，让网关返回明确的 `no_capable_upstream`。
3. **owner 必须是真实账户**。`recordContribution` 对不存在的 user 只会 `AddCredits` 失败并打日志（[internal/hub/contribution.go:51](../internal/hub/contribution.go)），钱会静默消失。不要用 `"platform"` 这种假 ID 播种。
4. **公网档会做 DNS 解析**（[internal/hub/gateway.go:907](../internal/hub/gateway.go)）。服务器 DNS 抖动时播种会失败——所以播种必须非致命，且重启可重试。
5. **注册是邀请制**（`--public` 强制 `--signup-invite`），但新用户仍有 20 点赠额（[internal/hub/policy.go:89](../internal/hub/policy.go)）。自营上线后这是真实支出，必须配合 §4 第 4 项和 P1-1 的限额。
6. **不要把"中转站"做成第二套 API**。所有配置最终都要落到 `upstreams` 表，这样真实 provider 接入时才有统一的调度面。
7. **不要在启动时覆盖控制台的手工修改**。播种只管"不存在则创建"，不管"存在则同步"。
