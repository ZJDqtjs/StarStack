## 一、选题背景与研究意义

### 1.1 现实背景

中心化云计算把异构算力封装成规格统一、租期稳定的实例，代价是价格高、供给集中，且必须为峰值容量买单。与此同时，大量消费级 GPU、游戏主机、轻薄本、边缘设备在多数时间处于闲置状态——一台游戏显卡的日均高负载时长往往不足两小时。这部分算力有三个共同特征：**不稳定**（随时可能被主人关机或断网）、**不可信**（回传结果无人担保）、**高度异构**（编码器、显存容量、指令集、运行时版本互不相同）。

现有商业方案没有真正解决这三性：包年包月云厂商出售的是稳定资源池，闲置零售类平台（vast.ai、Salad 一类）做的是"整机出租"，把不稳定算力当成稳定算力来卖，因此只能承接容错性高的长任务，无法支撑需要多节点同时就绪的分片任务。用户侧的真实痛点是二元对立的：需求方想要"比云便宜且按量结算"，提供方想要"挂上去就能赚、掉了线不倒扣"。这两件事在技术上由**调度层如何度量同时可用性**与**交易层如何度量已消耗算力**决定，而这正是当前中间层软件缺乏公开实现与实测数据的环节。

### 1.2 学术意义

本课题聚焦的问题是：**当算力供给本身是概率性的，调度与交易该如何耦合？** 传统调度（Kubernetes/Slurm 一类）假设节点集合在任务生命周期内基本可用，其失败处理是"重调度"；而闲置算力池中，单节点离线是常态事件而非异常事件，失败处理必须与结算联动——一个被回收的重算分片不该向买方二次收费，一个已完成却迟到的回传不该白拿报酬。计价又反过来影响调度：提供者可以自由改价，调度器必须在"便宜"与"可靠快"之间做加权，而这个权重会改变整个市场的成交结构。

本课题的贡献不在于造一个更快的分布式运行时，而在于给出**一个可复现的中间层实现 + 一组来自真实账本的对照实验数据**，用于回答"闲置算力场景下，调度策略与交易机制的耦合设计能带来什么"。

### 1.3 系统定位与边界

**做**：资源注册与能力发现、任务画像与分片规划、两阶段匹配调度、租约与容错回收、结果校验、计量结算与账单、多端接入控制台、策略对照实验。

**不做**：自研分布式计算运行时（不实现容错协议、一致性算法、网络分区处理）；不自研执行内核（转码用 FFmpeg、渲染用 Blender、虚拟化用 QEMU/KVM、推理用 llama.cpp/vLLM/ComfyUI）；不引入区块链与代币经济；不做真实法币支付通道（账本用积分记账，复式流水结构已预留接支付的位置）。

底层执行容器化底座复用 Docker/K3s 的设计在实现过程中做了务实收敛：闲置算力接入的现实前提是"把 9 MB 静态二进制拷到那台机器上就能跑"，因此执行层走**FFmpeg/Blender/QEMU 子进程 + 出站长轮询**路线，容器化作为部署选项而非硬依赖。这一调整记录在 4.4 节。

## 二、国内外研究现状综述

**（1）公共算力共享。** BOINC（Anderson, 2004; 2019）确立了"志愿者贡献空闲算力"的范式，其成果校验依赖同任务多副本交叉比对，代价是算力翻倍；SETI@home 类任务天生可分割且幂等，因此不需要交易层。本课题面对的是**非幂等且有成本**的任务（渲染一帧、转码一段、跑一次编译），副本比对不经济，因此转向"哈希校验 + 分段释放报酬 + 信誉"的半可信机制。

**（2）去中心化算力市场。** Golem、iExec、Akash 等把撮合与结算放到链上，用智能合约担保租赁。其代价是：结算延迟与 gas 成本、以及"链上无法验证计算是否真的做了"这一根本缺陷。本课题明确不采用链上结算，改用**平台内积分账本 + 平台作为验证方**，并把"完全去中心化验证在闲置算力场景下代价过高"作为论文中需要论证的论点之一，用实测的重派与迟到回传拒绝数据支撑。

**（3）异构算力调度。** Kubernetes/K3s 的调度器假设节点稳定且资源可通过 device plugin 精确申报，其 `requests/limits` 模型不表达"这个节点有 60% 概率在十分钟后还在线"；Volcano/Kubeflow 的 Gang Scheduling 解决"一组容器同时就位"，但仍以静态资源池为前提。本课题把**同时可用性**作为调度评分的显式输入，并提供从真实心跳流水推算在线率的实现路径。

**（4）分布式推理服务化。** llama.cpp 的 `rpc-server` 与 `--n-cpu-moe`、vLLM 的张量并行、SGLang 的前缀缓存、Petals 的端到端分片推理，共同说明"模型可以按层/按专家切分"这一工程事实；但它们各自面向已知、可控的机器组。本课题把这些引擎当作**上游执行体**，平台层负责按模型能力与上下文长度做低价路由、按 token 三段计价、会话粘性以复用前缀缓存——这一层在公开实现中几乎是空白。

**（5）闲置算力定价。** 云厂商的 Spot/抢占式实例由平台单方定价并随时可回收；闲置算力市场里定价权在提供者手上，平台只能抽佣。本课题采用"提供者自定价 + 平台按撮合金额比例抽佣（当前 90/10）+ 分时系数"的方案，把峰谷定价与调度拥塞的耦合留作对照实验。

**现有工作的共同缺口**：有调度器不讲钱，有市场不碰调度。调度评分与结算口径分属两套系统时，"便宜但不可靠的节点该不该接活""涨价发生在分片飞行中算谁的"这类问题无人回答，也缺乏可复现的实测数据。本课题正是补这一层。

## 三、研究目标与主要研究内容

### 3.1 总目标

实现一个可演示、可部署、可采集实验数据的调度与交易中间平台，使同一套「资源注册 → 任务画像 → 分片规划 → 约束匹配 → 派发执行 → 结果校验 → 计量结算 → 掉线退款」骨架，能承载**至少五种粒度不同的任务画像**，并给出调度策略与定价机制的三组对照实验数据。

### 3.2 任务画像（系统内部统一抽象）

所有场景在平台内统一为同一张任务描述规范，差异只体现在约束字段与切片单位上，而不是各自独立的子系统：

| 任务画像 | `kind` | 切片单位 | 关键约束字段 | 合并/交付方式 | 实现状态 |
|---|---|---|---|---|---|
| 视频转码 | `transcode` | 视频秒（关键帧对齐） | 编码器、GPU、核数、内存、运行时 | concat demuxer + `-c copy` 无损拼接 | **已实现并有实测数据** |
| Blender 渲染 | `blender` | 帧 | 引擎、采样数、分辨率百分比、帧范围 | 帧序列解压排序 → ffmpeg 编码成片 | **已实现** |
| PR/FCP 时间线 | `pr` | 视频秒 | 交换格式可还原范围、素材文件名匹配 | 本地 concat，参数不一致自动转码兜底 | **已实现** |
| 程序编译打包 | `build` | **整片不可分** | 构建运行时（`--allow-build` + 能力上报）、超时 | `result.zip` 回传（含 `build.log`），按墙钟分钟结算 | **已实现**（用作"分片粒度的反面参照"） |
| LLM 推理服务 | 网关 | token | 上下文长度、能力位（工具调用/JSON/图像/确定性/前缀缓存） | 流式 SSE 直返，三段计价 | **已实现**（OpenAI 兼容网关） |
| AI 视频生成 | ComfyHub | 流水线阶段 | 主节点生成 latent → 中端 VAE 解码 → CPU 封装 | 编排器按阶段派发 | **已实现**（三 agent 分阶段编排） |
| 云电脑 / 临时主机 | `vm` | 租期秒 | vCPU/内存/磁盘 ≤ 物理容量、镜像 SHA-256、IPv6 GUA 归属校验 | QEMU + cloud-init，VNC/SSH 端点 | **已实现**（slirp 与 routed 两种 IPv6 接入） |

"编译打包"这一类刻意做成**不可分割的单一分片**：真实依赖图切分本身就是独立研究问题，把它作为对照组放进实验，正好用来论证"分片粒度不是越细越好"——带宽、启动开销、依赖闭包都会吃掉并行收益。

### 3.3 四个拟解决的关键问题

**K1 闲置算力的同时可用性评估。** 基于提供者历史在线率与心跳流水，计算"需要 N 个节点同时就绪"的多节点任务的实际可调度概率；对比"按总容量贪心匹配"在相同负载下的失败率与重派率差异。

**K2 异构任务的分片粒度权衡。** 量化按帧（渲染）、按秒（转码/时间线）、按专家或层（推理）、不可分（编译）四种粒度下任务完成时间、调度开销与产物质量的三角关系，并给出物理上限：源视频 GOP 密度决定转码任务可切分的最大片数（实现中已出现"要求 8 片实得 5 片"的可观测现象）。

**K3 分时定价与调度拥塞的耦合。** 在调度器与报价接口内置峰谷系数，通过模拟与小规模实测对比固定定价与分时定价下的资源利用率、拒单率、任务排队时长与平台抽佣收入。当前评分函数中的价格权重（演示档 0.5 / 公网档 0.75）是经验常数，本课题要回答"这个值怎么定"。

**K4 半可信交易机制。** 用信誉分、结果轻量校验（提供者自报 SHA-256 与平台独立重算双一致）、分段释放报酬、预扣—检查点释放—完成结算—掉线退款的租约模型，论证"完全去中心化验证在该场景下代价过高"，并给出在 at-least-once 派发语义下**不重复计费**的具体机制。

### 3.4 研究内容分解

1. **资源接入与能力发现**：Agent 启动即对本机做一次完整探测（核数、内存、可用磁盘、`nvidia-smi` 显卡、FFmpeg **实测可用**的编码器集合 libx264/x265/nvenc/qsv/amf/svt-av1、运行时版本、QEMU 与硬件加速器），按白名单字段上报，杜绝自报虚高。
2. **NAT 后节点的接入与信任建立**：所有通信由节点向平台**主动出站**发起，家庭/宿舍网络无需开任何入站端口；一次性启动码 → 按节点 ID 派生 HMAC 凭证（`X-Node-Secret`），把"我是谁"从自称变成可验证事实。
3. **两阶段匹配调度**：硬约束过滤（编码器/GPU/核数/内存/运行时/架构/价上限）→ 软评分排序；派发即占槽、派发瞬间冻结该分片单价、分片级 `Excluded` 名单、连续失败停派、按空闲槽公平分配给排队任务以防饿死。
4. **租约容错与结算正确性**：租约 = `45s + 2×分片时长`；回收扫描按分片驱动而非按节点驱动；被回收后老节点的迟到进度/失败/产物一律拒绝（409），已完成分片不被改写或二次结算；任务级墙钟超时判失败并退还预扣。
5. **交易与计量**：保守预扣（最贵可行节点 × 整片时长）、按实际算力秒结算、差额退还、90/10 分成、复式账本流水、按节点收益报表、跨重启恢复与不重复结算。
6. **多端接入层**：Web 控制台（9 视图）+ 安卓 App + 桌面客户端 + 微信小程序，四端共用同一套接口层与状态约定。
7. **安全与部署档位**：同一二进制通过 `--public` 切换策略档位，公网档关闭"任意文件读"（Broker 本地路径）、"抢他人算力"（待认领列表）、"白送点数"（自助充值），并强制注册邀请码、Agent 接入令牌、带过期时间的签名源文件 URL、按 IP 的登录限流、systemd 资源与文件系统隔离。

### 4.3 关键设计决策与理由

| 决策 | 理由 |
|---|---|
| 语言选 **Go 单一 codebase**，而非提案原定的 Python(FastAPI) | 交叉编译产出免依赖静态二进制（六平台：win/linux/darwin × amd64/arm64），"拷过去就能跑"是闲置算力接入的现实前提；同时避免一人开发在 Go/Python 间切换 |
| 通信选 **Worker 主动发起的 HTTP 长轮询** | NAT 后节点没有公网 IP 与端口，出站长轮询让穿透天然成立；协议层已隔离，可平替为 gRPC stream/WebSocket |
| 状态选 **SQLite（纯 Go 驱动，免 CGO）** | 租约回收与按量结算必须能跨重启验证，内存态不够；纯 Go 驱动才能维持"一个二进制"前提 |
| 评分中价格项写成**与池均价的比值再取幂** | 使该项无量纲：市场整体成交在 0.1 点/秒还是 10 点/秒，平台的相对偏好不变，实验系数才可移植 |
| 结算用**派发时冻结的 `seg.PriceAt`**，而非节点当时单价 | 买方授权的是"这一片在这个价上"，节点跑到一半涨价不应由买方买单 |
| 未做 GPU 硬隔离（MIG/vGPU），当前依赖 NVENC 并发能力 | 实验室不具备稳定的 Ampere 多租户卡；作为论文中"多租户超卖需要 MIG 切片"的设计项与局限声明 |

### 4.4 与早期提案的范围差异（需在开题时向导师说明）

1. 执行底座从"K3s 优先"收敛为"子进程 + 长轮询优先，容器化作为部署选项"，理由是接入摩擦与免运行时二进制；提案中已预留这条退化路径。
2. 交付范围从"至少一条真实链路"扩大到**五条已跑通的链路**（转码、Blender、时间线、编译、推理网关）加一条虚机租期链路和一条 ComfyUI 流水线，其中前一条有完整实测数据。
3. 前端从"Vue/React 展示资源视图"细化为**四端**（Web/安卓/桌面/小程序），并确定不采用 Flutter——本产品的界面是数据密集型仪表盘与 API 客户端，Web 技术栈生态（图表、流式日志、终端、noVNC 类资产）更契合，且能复用同一套接口层。
4. 新增"多端接入与部署安全档位"这一研究内容：同一份代码在演示与公网两种威胁模型下的行为差异，是原提案未涵盖、实现中被事实证明必须设计的部分。

## 五、关键技术与创新点

**创新点 1：跨粒度任务画像的统一骨架。** 把按秒、按帧、按 token、按租期、不可分五种切片语义收敛到同一套"规划 → 派发 → 校验 → 合并 → 结算"流程，差异化只落在约束字段与执行适配器上。这不是纸面抽象：平台已在同一调度器与同一账本上跑通全部五类，编译任务作为"不可分"特例进入同一模型。

**创新点 2：at-least-once 派发下的抗重复计费机制。** 闲置池里"慢节点重交一次同样的活"可直接白拿钱，一次伪造的"失败"回报还能把别人正在跑的健康的分片标记为失败。系统用**租约所有权校验 + 分片级 Excluded + 迟到回传 409 拒绝 + 已完成分片不可改写**四条约束，在不引入分布式共识的前提下保证计费正确，并有重启恢复实测佐证（账本无重复结算）。

**创新点 3：定价与调度耦合的可观测评分函数。** `score = 实测吞吐 × 信誉 × (可行池均价 ÷ 该节点单价)^w / (1 + 当前占用)`，其中吞吐是历史分片的指数滑动平均、新节点取探针值 1.0 参与竞争（试用期探索的最小实现）。该公式**在控制台报价里原样展示**，并通过 `/api/quote` 返回这一片的 `first_pick`——买方看得见"谁会接到活、为什么是他"。实测已观察到关键现象：两台同硬件节点在都没有历史吞吐时低价者被选中，一轮之后高吞吐项压过价格项、首选翻回贵节点。这正是 K3 实验要系统化的对象。

**创新点 4：NAT 环境的低摩擦信任建立。** 一次性启动码（仅授权单个节点 ID、绑定铸码账户、30 分钟有效、注册即花掉）→ 按节点 ID 派生 HMAC 凭证 → 节点凭据按 ID 落盘（同机双击两个脚本不会串用身份）。文件名按节点 ID 而非统一 `node.key`，是因为 Broker 把它当作"这台机器是该节点"的证据。

**创新点 5：部署档位作为一等公民。** 同一二进制用 `--public` 切换威胁模型，公网档关闭三项演示便利（本地路径读、待认领列表、自助充值），前端据此**自适应收起**服务端必然拒绝的入口，避免留下可点击的死路。

## 六、实验方案设计

实验环境：2–3 台真实机器 + 模拟节点，不追求节点规模。开发机为 AMD Ryzen 7 6800H（16 核）/ RTX 3060 Laptop；公网 Broker 部署于 Azure 虚机。

### 6.1 评价指标定义

| 指标 | 定义 | 数据来源 |
|---|---|---|
| 分片并行度 | Σ分片耗时 ÷ 分布式墙钟 | `jobs`/`segments` |
| 真实加速比 | 单机基线墙钟 ÷ 分布式墙钟 | Broker 同机同参数跑完整转码，**不产生分片、不计费** |
| 校验一致率 | `verified=true` 分片数 ÷ 总分片数 | 提供者自报哈希与平台独立重算双一致 |
| 重派率 | `attempt>1` 的分片占比 | `segments.attempt` |
| 计费平衡偏差 | 预扣 −（实结 + 退还） | `ledger` 复式流水，期望恒为 0 |
| 产物质量偏差 | 拼接时长溢出、体积比基线增幅 | ffprobe 全片解码校验 |
| 同时可用成功率 | N 节点 gang 任务在截止前全部就绪的概率 | 心跳流水离线计算 |

### 6.2 三组对照实验

**E1 同时可用性（对应 K1）**：从 `nodes` 表的历史上下线时间戳与 `last_seen` 提取每台机器在线率与在线时段分布；构造"需 N 节点同时就绪"的负载，用离线重放/模拟对比**贪心按总容量匹配**与**同时可用性评分**两策略的完成率、重派率、墙钟。产出：一张"节点数 vs 可调度概率"曲线，以及"按容量贪心在高 N 下失败率陡增"的实证。

**E2 分片粒度（对应 K2）**：固定输入源片，扫描分片数 1→物理上限，测量墙钟、并行度、产物体积与时长溢出，并记录 GOP 密度导致的实际上限；同构地扫描 Blender 帧区间划分与 llama.cpp 的 `--n-cpu-moe` offload 比例；编译任务作为不可分对照组，量化"切不开时"的墙钟。产出：三类粒度的收益拐点与物理上限的可观测证据。

**E3 分时定价（对应 K3）**：在调度器与报价中注入峰谷系数，模拟到达过程的需求，对比固定定价与分时定价下的利用率、拒单率、排队时长、平台抽佣；同时扫描价格权重 `w`，回答"评分式而非价低者得"的取舍边界。产出：`w` 的敏感性分析，把当前经验常数 0.5/0.75 换成有数据支撑的取值。

**E4 结算正确性与抗欺诈（贯穿性验证）**：故障注入（跑到一半强杀持有分片的节点）、迟到回传（被回收后老节点再交产物）、飞行中改价、未认领节点结算缺口四类场景，验证账本平衡、409 拒绝、冻结价生效，并把"未认领节点点数无处可付"这一已知缺陷量化为需要托管账户（escrow）的证据。

### 6.3 已完成实测数据（原型有效性证据）

**第一轮**（纯调度链路，60s 1080p→720p，4 分片，libx264 veryfast）：分片耗时之和 24.8s，分布式墙钟 7.5s，单机基线 10.9s，真实加速比 1.45×，分片并行度 3.3×，哈希校验 4/4 一致，拼接产物 60.1s 全片解码无错误。

**第二轮**（含账户、鉴权、按节点单价，全部走登录后 Web/API 路径）：6 分片墙钟 15.3s，分片之和 46.1s，并行比 3.01×，加速比 1.36×，6/6 哈希一致，预扣 60.00 → 实结 54.00 → 退还 6.00，界面显式显示退还流水，按节点收益分别入账。

> 上述两轮的加速比均为**同机三进程争抢同一组 CPU/GPU**、且基线与分布式任务并发跑测得。其诚实解读是：分片调度链路已打通、切分与派发是正确的（并行度 3.0× 以上），1.36–1.45× 由单机资源上限决定，不代表跨机部署收益。**这个现象本身即论文论点之一**：加速比受节点异构性与同时可用性约束，不是节点数的线性函数。跨机三台（一台台式机 + 一台轻薄本 + 一台旧游戏本）实测将在 E1 阶段补齐。

**容错实测**：6 分片任务第 12 秒强杀持有 #4/#5 的节点，4 秒后该分片被回收并由存活节点以 `attempt=1` 接手重算，SHA-256 一致，6 片各结算一次共 60.000 点，产物 60.145578s 解码无错误——节点掉线不再让任务永久卡死。

**跨重启恢复实测**：任务在飞时杀 Broker 并原样拉起，2 节点与 1 未完成任务装回，旧 Cookie 仍有效，在飞分片回退 `pending` 且 `attempt+1` 重派跑完，账本无重复结算，预扣 60.00 → 实结 54.00 → 退 6.00 → 余额 100.00；跨重启墙钟含停机窗口，系统**主动拒绝计算加速比**并标记"跨 Broker 重启恢复"（宁可少一个数字，不要一个没意义的数字）。

**验收与回归**：11 步端到端 smoke（匿名越权、硬约束不可派发、分片全校验、按节点单价结算、改价权限、隐私脱敏）、调度/结算核心单元测试（不依赖 ffmpeg，直接构造节点池）、云主机专项测试、Playwright 在真实浏览器覆盖卖方/买方 × 浅深色 × 宽窄屏且无 JS 错误与横向溢出。

## 八、可行性分析

**（1）工程可行性——已由实现证明。** 核心链路不在计划里，而是已经跑通并有两轮实测数据；五类任务画像共享同一调度器与同一账本，证明统一抽象站得住；1.53 万行 Go 后端 + 四端客户端 + 公网部署件已入库，剩余工作集中在**实验与建模**这一低风险区间。

**（2）硬件可行性。** 单人开发机（16 核 + RTX 3060 Laptop）足以支撑 Broker 与多 Agent 并发演示；已有 Azure 虚机（891 MB 内存规格，systemd 资源上限 512 MB 约束下稳定运行）作为公网入口；实验设计只需再加 1–2 台真实异构机器（宿舍台式机 + 旧笔记本），模拟节点补足规模，与提案"2–3 台真实机器 + 模拟节点"的判断一致。

**（3）数据可行性。** 实验所需字段**已经在库里**：节点上下线时间戳与 `last_seen`（在线率）、`segments.attempt`（重派率）、分片墙钟与冻结价（粒度与定价）、`ledger` 复式流水（计费平衡）。E1/E3 属于离线分析与模拟，不需要扩大真实节点规模。

**（4）理论可行性。** 评分函数、租约模型、预扣口径均为显式实现且有单元测试兜底，不是隐式行为；策略层（信誉加权、分时系数、可用性惩罚）与执行层解耦，改策略不动二进制分发链路。

**（5）一人开发可行性。** 单一 Go codebase、零构建链前端（`go:embed` 单文件）、免 CGO 依赖、纯标准库的 ComfyHub 组件——每一项都在降低维护面；部署脚本只做加法、不改机器上已有的服务。

## 十、可能遇到的困难与对策

| 困难 | 影响 | 对策 |
|---|---|---|
| 真实闲置节点稀缺，在线率样本不足 | E1 曲线噪声大 | 用历史心跳重放 + 参数化模拟补足，真实样本用于校准模拟分布而非替代 |
| 拼接时长 ~0.1s 溢出、产物体积 +5% | 交付质量争议 | 分片头写入容器级时间戳修正，或音轨走 `-c:a copy` + 独立切分；论文中作为分片代价量化 |
| 源片整片下载到节点，带宽成瓶颈 | 大文件不可扩展 | 改 HTTP Range 区间请求或预切片；这恰好是 K2"粒度不是越细越好"的反面案例 |
| 分片产物未进对象存储，宕机时正在上传的片丢失 | 白烧算力 | at-least-once 语义已兜住正确性；接 MinIO/S3 + 租约流水单表，列入完善阶段 |
| 未认领节点"扣买家但无人可付" | 结算公平性缺陷 | 引入托管账户（escrow），提供者完成认领后补发；代码中已定位到 `settleSegment()` |
| 评分系数全是经验常数 | 策略结论可信度 | E3 做 `w` 敏感性扫描，用数据替掉拍脑袋值 |
| QEMU 真机开虚机未在本机跑过（开发机无 qemu） | 云主机链路存在未验证面 | 到有 KVM/WHPX 的机器上先用一台 Ubuntu cloud image 冒烟；正确性目前由 seed ISO 解析、IPv6 回环转发测试与 QMP 参数构造支撑 |
| 无浏览器内虚机控制台（仅返回 `vnc://` + 一次性口令），VNC 明文且口令强度弱 | 用户体验与安全 | 建议买方走 SSH 隧道；后续补 noVNC/WebSocket 网关，列入扩展工作 |
| 一人开发范围易失控 | 毕设按期完成风险 | 严守"不做自研运行时/不上链/不做支付"边界；新特性必须先回答"是否服务于四个关键问题之一" |

## 十一、恳请导师指导的问题

1. 执行底座用**子进程 + 出站长轮询**（当前实现）还是回到 **K3s/Docker 容器化**更符合实验室条件与答辩预期？前者接入摩擦低，后者与主流云原生叙事一致。
2. 核心演示链路应以**视频转码**（已有两轮实测与容错数据）为主线，还是把**推理网关/MoE 分片**提到主线以贴近当前 LLM 热点？
3. GPU 隔离缺失（无 MIG/vGPU，依赖 NVENC 并发）在答辩中如何界定——作为书面设计与实验局限是否足够？
4. 手机 NPU 接入作为异构资源抽象的扩展案例（讨论其"短时突发、可中断"的任务形态约束）是否足够，还是需要至少纳入实验对比？
5. 三组对照实验中，E1 依赖真实在线率样本，实验室能否协调到 2–3 台**长期开机**的异构机器（不必是显卡机，普通笔记本即可）？
6. 编译打包任务当前刻意做成不可分单片，作为 K2 的反面参照——这个取舍在论文里的分量是否合适，还是需要真的实现按模块依赖分组？
